## 1. 背景：为什么要升级

### 1.1 现状链路（Naive RAG）

当前系统的问答流水线只有一条直线：

```
用户问题
   │
   ├─► ① 问题向量化（gemini-embedding-001，768 维）
   │
   ├─► ② pgvector 检索 top3（余弦相似度，阈值 0.3）
   │
   ├─► ③ 把 3 个文本块拼进 system prompt
   │
   └─► ④ gemini-3.6-flash 流式生成回答
```

这个链路叫 **Naive RAG**（朴素检索），它的特点是"一条路走到黑"：一次向量检索，拿到啥就答啥，没有纠错、没有二次确认。

### 1.2 四个已知痛点（每个都对应一个升级需求）

| # | 痛点 | 生活化例子 | 根因 |
|---|------|-----------|------|
| P1 | **关键词漏检** | 文档里写"费用报销流程"，你搜"报销"——语义相似但字面不同，向量距离不够近，可能掉出 top3 | 纯向量检索只认"语义"，不认"字面"；专有名词、缩写、编号（如"KPI-007"）尤其吃亏 |
| P2 | **追问断片** | 你先问"报销流程是什么"，再追问"那要多久到账？"——"那"指代不明，检索时直接按原话搜，搜出牛头不对马嘴 | 多轮对话的检索用的是"原问题"，不是"补全后的问题" |
| P3 | **粗召回太粗** | 一次只取 top3，真正相关的块排在第 5 名就被丢掉了；反过来，top3 里可能有 2 块是废话 | 没有"先广撒网、再精挑"的两阶段思想，一步到位取 3 块 |
| P4 | **切块切坏语义** | 一份 2000 字的制度，硬切成 500 字一块，把"责任分工"表格拦腰切断，答案支离破碎 | 分块逻辑是"按段落 + 超长硬切"，不感知句子和标题 |

### 1.3 痛点 P5：复杂问题单跳搞不定

还有一个更高级的痛点在当前架构里**完全无解**：

> 用户问："对比《报销制度》和《差旅制度》对发票的要求有什么不同？"

这类问题需要**同时检索两个不同主题的文档**。单跳检索（一个问题 → 一个向量 → 一次查询）物理上做不到——一个 768 维向量只能"靠近"一个主题，不可能同时靠近两个。

这就是 **Agentic RAG（多跳检索）** 要解决的问题：让模型像人一样，自己决定"先查 A，再查 B，然后对比"。

## 2. 目标与非目标

### 2.1 目标（做什么）

1. **检索质量可感知地提升**：回答的引用来源相关性明显变好，漏检率下降
2. **多轮追问不再断片**：代词/省略问题能正确补全后再检索
3. **复杂对比问题能答**：支持"跨主题拆解检索"（多跳）
4. **过程可观测**：能调试每一步检索发生了什么（对学习者尤其重要）
5. **保持流式体验**：改动不破坏现有打字机效果和多轮对话

### 2.2 非目标（不做什么，防止范围膨胀）

| 不做的事 | 原因 |
|----------|------|
| 不换数据库（不迁移到 Elasticsearch/Meilisearch） | 数据量级（几十个文档、几百块）完全不需要重武器，Postgres 够用 |
| 不做用户认证/多租户隔离 | 属于 Phase 4，与检索升级无关，避免混入 |
| 不做前端大改 | 本轮只动后端检索链路，前端仅可能加一个"检索过程"调试面板 |
| 不做文档重解析（历史文档不重跑） | 分块优化只对新上传文档生效；旧文档如需生效，提供一键重处理即可 |

## 3. 功能需求

### FR1：混合检索（Hybrid Search）

> 解决痛点 P1（关键词漏检）

**需求描述**：检索阶段不再只靠向量，而是**双通道召回**：

- **通道 A（向量）**：语义相似度检索（现有能力）
- **通道 B（关键词）**：从问题中提取关键词，做字面匹配检索

两条通道的结果**合并去重**后，再统一排序进入下一阶段。关键词通道对中文专有名词、编号、缩写、人名地名特别有效。

**典型场景**：
- 文档写"入职材料包括：身份证、学位证、体检报告"，用户搜"要带身份证吗"——向量能命中；用户搜"学位证"——关键词通道兜底命中
- 文档写"项目代号 KK-1024"，用户直接搜"KK-1024"——向量几乎必然失手（语义层不认字符序列），关键词通道必中

**验收标准**：
1. 构造 10 个"字面不同但语义相同" + 10 个"字面相同"的测试问题，混合检索相比纯向量的命中率（top3 内包含正确答案）提升至少 20 个百分点
2. 检索延迟增加不超过 150ms（关键词通道为数据库直查，不应显著拖慢）
3. 混合检索结果中不含与问题完全无关的块（由人工抽查 20 个结果）

**优先级**：P0（地基，其余功能都建立在它之上）

---

### FR2：查询改写（Query Rewriting）

> 解决痛点 P2（追问断片）

**需求描述**：检索之前，先用一次轻量 LLM 调用，把"当前问题 + 最近对话历史"改写成**可独立检索的问题**，并顺带提取**搜索关键词**。

改写分两部分输出：
1. **standalone_question**：补全代词的独立问题（"那要多久到账？" → "报销流程中，款项到账需要多久？"）
2. **keywords**：2~6 个搜索关键词（供 FR1 的关键词通道使用）

**典型场景**：
- 用户："报销流程是什么？" → AI 回答 → 用户追问："那要多久到账？"
- 不改写：按"那要多久到账？"去检索 → 大概率搜不到
- 改写后：按"报销流程 到账 需要多久"检索 → 命中

**验收标准**：
1. 连续 5 轮追问（包含"它/这个/那/然后"等指代词），每轮检索到的块与当前话题相关
2. 改写输出格式稳定为 JSON（解析失败率 < 5%，失败时降级用原问题）
3. 每次改写额外增加一次 LLM 调用，延迟增加可接受（见 NFR-1）

**优先级**：P0（与 FR1 配合使用，关键词来自这里）

---

### FR3：两阶段检索 —— 粗召回 + 重排序（Rerank）

> 解决痛点 P3（粗召回太粗）

**需求描述**：把现在的"一次取 top3"改成**两阶段**：

```
阶段一（粗召回）：混合检索取 top20 候选块（广撒网）
阶段二（精排序）：把 20 个候选块交给 LLM 挑出最相关的 top3（精挑）
```

为什么 20 这个数？因为向量检索的"相关排名"噪声很大——真正相关的块经常排在 5~15 名之间，取 20 能覆盖绝大多数情况，又不会把 prompt 撑爆。

**典型场景**：知识库有 100 块文本，问题真正相关的只有 4 块，其中 1 块向量排名第 11 名。旧方案直接丢掉；新方案先进候选池，再被 LLM 捞回来。

**验收标准**：
1. 与 FR1 相同测试集下，rerank 后 top3 的命中率 ≥ 80%（比粗召回 top20 略降属正常，因为取 3 个）
2. 最终送入生成的 3 块中，无重复主题块（同一文档相邻段落最多取 2 块，防信息冗余）
3. rerank 为一次性 LLM 调用，不引入循环

**优先级**：P1

---

### FR4：智能分块（Chunking 优化）

> 解决痛点 P4（切块切坏语义）

**需求描述**：重写分块逻辑，遵循三条原则：

1. **句子感知**：优先在句子边界（。！？换行）切，不再硬切 500 字符
2. **标题感知**：识别 Markdown 标题（`#`/`##`），以标题为分块锚点，并把"标题路径"（如 `公司制度 > 报销管理 > 报销流程`）作为前缀附加到每块内容上——这样每块自带上下文，检索"报销流程"时连带着把"这是报销管理章节的"信息也带出来
3. **结构保护**：表格（Markdown 表格/换行对齐的内容）尽量整块保留，不拦腰切断

**典型场景**：一份《员工手册.md》，包含 `## 报销流程` 和 `### 常见问题`。旧逻辑可能把两个标题的内容混进同一块；新逻辑以标题为界切块，且每块开头都有标题路径，检索"发票丢失怎么办"能命中"报销流程 > 常见问题"块并知道它属于报销章节。

**验收标准**：
1. 对同一份测试文档，新旧分块结果人工对比：新方案无"一句话被切断"的块（抽查 50 块，断句率 = 0）
2. 每块默认携带标题路径（有标题的文档）
3. 旧文档提供"重新处理"入口（复用现有 processing 流程，重跑 parse → chunk → embedding）

**优先级**：P1（与 FR1/FR2 无强依赖，可并行）

**注意**：FR4 改变的是分块结果，**历史文档需要重跑**才生效。非目标中已说明提供一键重处理，不强制迁移。

---

### FR5：Agentic 多跳检索（Multi-hop Retrieval）

> 解决痛点 P5（复杂问题单跳搞不定）

**需求描述**：为系统增加"检索 Agent"能力，支持两种工作模式：

**模式一：查询规划（Query Planning）—— 推荐先做**

```
复杂问题
  → LLM 拆解成 N 个子问题（规划器）
  → 每个子问题独立走"改写 + 混合检索"
  → 合并所有子问题的结果（去重，最多留 6~9 块）
  → 一次生成最终回答
```

特点：**可控、可预测、延迟低**（并行检索），适合"对比两个主题""并列罗列多条件"类问题。

**模式二：ReAct 循环（自主 Agent）—— 进阶**

```
问题 → LLM 思考 → 决定调工具 search_knowledge_base("...")
     → 看到检索结果 → 不够？再调工具 → 够了 → 输出最终回答
```

特点：**灵活、能处理链式推理**（"A 的负责人是谁 → 他负责过哪些项目"），但延迟高、可能绕圈（需要设置最大迭代次数）。

**典型场景**：
- 规划模式："对比《报销制度》和《差旅制度》对发票的要求" → 拆成 ["报销制度 发票要求", "差旅制度 发票要求"] → 并行检索 → 汇总对比
- ReAct 模式："《员工手册》里说请假要找谁审批？他负责哪些事情？" → 第一跳查到"找王经理" → 第二跳搜"王经理 职责"

**验收标准**：
1. 规划模式：对 10 个跨主题测试问题，最终回答引用的块覆盖 2 个以上不同主题文档（对比类问题不再"一边倒"）
2. 规划模式延迟：子问题并行检索，总延迟 ≈ 单次检索 + 改写，不随子问题数线性增长
3. ReAct 模式：最大迭代次数 5（防死循环）；10 个测试问题中 8 个在 3 跳内完成
4. 单跳能答的问题（简单问题）默认走原流水线，不被 agentic 拖慢（路由判断）

**优先级**：P2

## 4. 非功能需求（NFR）

| 编号 | 需求 | 指标 |
|------|------|------|
| NFR-1 | 检索链路延迟 | 改写 + 混合检索 + rerank 的**纯检索部分** ≤ 1.5s（不含最终生成）；单问题（不触发 agentic）总链路 ≤ 4s 首字 |
| NFR-2 | 成本预算 | 每次问答的 LLM 调用次数：单跳 ≤ 3 次（改写 1 + rerank 1 + 生成 1）；多跳 ≤ 改写 1 + 生成 1 + rerank N + 规划 1，封顶 8 次 |
| NFR-3 | 可观测性 | 每轮检索输出结构化日志：各阶段耗时、候选块数量、命中来源标题、rerank 前后排名变化（用于学习调试） |
| NFR-4 | 降级策略 | 任一新环节失败（LLM 超时/解析失败），自动降级为"旧链路"（纯向量 top3），不中断用户问答 |
| NFR-5 | 兼容性 | 不破坏现有前端 SSE 流式协议；历史消息格式不变 |

## 5. 优先级与排期（规模估量）

按"地基 → 装饰 → 高级玩法"排序，每阶段都是可独立验收的增量：

| 阶段 | 内容 | 代码规模估量 | 预计工时 | 优先级 |
|------|------|-------------|---------|--------|
| **A** | FR1 混合检索（关键词通道 + RRF 融合） | ~150-200 行改动（新增 2 个文件 + 改 1 个） | 半天 | P0 |
| **B** | FR2 查询改写（含关键词提取） | ~100 行（新增 1 个文件，接进 chat 路由） | 2-3 小时 | P0 |
| **C** | FR4 智能分块（句子/标题感知） | ~150 行（重写 chunk-service + 加标题路径列） | 2-3 小时 | P1 |
| **D** | FR3 粗召回 + rerank | ~120 行（改检索配置 + 新增 reranker） | 2-3 小时 | P1 |
| **E** | FR5 规划模式（多跳） | ~250 行（新增 planner + 并行检索编排） | 大半天~1天 | P2 |
| **F** | FR5 ReAct 模式 + 调试面板 | ~300 行（工具调用循环 + 前端面板） | 1-2 天 | P2（可选） |

> 说明：工时按"你本人写 + 我讲解"的节奏估量；纯我代写可以压缩约一半，但学习收益会打折。

**依赖关系**：A ← B（B 提供关键词给 A 用，所以 B 至少提供"关键词提取"能力）；C 独立可并行；D 依赖 A；E 依赖 A+B+D；F 依赖 E。

## 6. 风险与开放问题

| # | 风险/问题 | 影响 | 应对 |
|---|----------|------|------|
| R1 | LLM 改写/rerank 不稳定（输出格式漂移） | 检索链路偶发异常 | 强制 JSON 输出 + 解析失败降级旧链路（NFR-4） |
| R2 | 多一次 LLM 调用 → 免费额度消耗变快 | 成本 | 改写用最小模型/最大裁剪；rerank 候选池限 20；设置日调用量封顶可后续加 |
| R3 | gemini-3.6-flash 高峰 503 | 改写/rerank 环节挂掉 | 重试 1 次 + 超时 8s + 降级（记忆里已有 503 踩坑经验） |
| R4 | 中文关键词提取质量（同义词、口语化） | 关键词通道噪音 | 关键词由 LLM 提取而非硬切词，接受少量噪音；RRF 融合时关键词通道权重略低 |
| R5 | ReAct 模式死循环 / 答非所问 | 体验差 | 最大迭代 5 次 + 每跳追加"目标约束"到 prompt + 可随时被路由切回单跳 |
| R6 | 历史文档分块不更新 | FR4 效果只在新区块体现 | 提供"重新处理"按钮（复用现有 processing 状态机） |

**开放问题（待用户拍板）**：
1. 是否需要"检索过程调试面板"（前端展示：改写了什么、关键词是什么、哪些块入选、rerank 前后变化）？——建议要，学习价值极高
2. ReAct 模式（阶段 F）是否纳入本轮，还是先只做规划模式（阶段 E）？
3. 混合检索的关键词通道，优先做"LLM 提取关键词 + 数据库匹配"（简单、中文友好），还是先调研 Supabase 的 pg_search（真 BM25）？（架构文档 3.3 有详细对比，建议前者）

## 7. 术语表

| 术语 | 含义 |
|------|------|
| Naive RAG | 朴素检索增强生成：一次向量检索 → 直接生成，无中间加工 |
| Hybrid Search | 混合检索：向量 + 关键词双通道召回后融合 |
| RRF | Reciprocal Rank Fusion，倒数排名融合：按排名而非分数合并两通道结果 |
| Rerank | 重排序：对粗召回候选做二次精排 |
| Query Rewriting | 查询改写：补全指代、提取关键词，让检索词更可搜 |
| Chunking | 分块：把长文档切成检索单元 |
| Agentic RAG | 让模型自主决定检索策略（拆解、多跳、循环） |
| ReAct | Reason + Act 循环：思考 → 行动（调工具）→ 观察结果 → 再思考 |

## 8. 补充需求：追平 2026 路线图（FR6~FR11）

> 本节点在 2026-08-09 补充。范围：与顶级系统（GraphRAG / Adaptive RAG / CRAG / Self-RAG / 评估 / 记忆）对齐的六大能力。
> 对应的架构设计见《architecture-retrieval-upgrade.md》第二部分（阶段 G~L）。

### FR6：评估体系（RAGAS 三指标）

**需求描述**：建设离线评估脚本 + 黄金测试集，用 LLM-as-judge 对每次检索/问答打分，输出可对比的报告。三个指标：**忠实度**（回答不瞎编）、**答案相关性**（不跑题）、**上下文精确率**（检索块准不准）。

**验收标准**：
1. 黄金测试集 ≥ 50 条，覆盖 5 类问题（简单/专有名词/追问/对比/多跳）
2. 每条问答输出三指标分数，报告含平均值与环比
3. 任一阶段改动后，分数回落超过 10% 能自动报警（或报告标注）

**优先级**：P0（先于一切后续阶段，它是迭代飞轮）

### FR7：自适应路由（Adaptive RAG）

**需求描述**：把 FR5 的规则路由升级为"规则 + LLM 判断"混合：规则命中走规则，未命中由一次轻量 LLM 调用判定 simple/complex，分流到单跳或 Agent 流程。

**验收标准**：
1. 10 个隐式对比问题（无"对比/区别"字样）能被正确判定为 complex
2. simple 问题不被 Agent 流程拖慢（走快速检索，延迟 < 3s 首字）
3. 路由判断失败时降级为 simple（保守优先，宁快勿错）

**优先级**：P1

### FR8：CRAG 质量门控

**需求描述**：检索后、生成前，对上下文做三态判断（correct/incorrect/ambiguous）。correct 直接生成；incorrect 触发补救检索（降阈值/换策略）；ambiguous 追加补充检索后合并。

**验收标准**：
1. 构造 10 个"检索必然跑题"的问题（如知识库外话题），其中 ≥8 个被判定 incorrect 并触发补救
2. 补救后最终回答的引用来源比补救前更相关（评估指标环比提升）
3. 门控判断失败时跳过门控，不阻塞生成（降级链 NFR-4）

**优先级**：P1

### FR9：Self-RAG 反射检查

**需求描述**：生成侧自检。生成前判断是否需要检索（简单问题直接答，省一次调用）；生成后对回答断言做"有依据/无依据"检查，无依据断言过多时重新生成一次（最多 2 次）。

**验收标准**：
1. 简单问候类问题（"你好"）不触发检索，直接回答
2. 对 10 条测试回答，post-check 能标出至少 80% 的"无依据断言"（人工核对）
3. 重生成次数上限 2，不无限循环

**优先级**：P2

### FR10：GraphRAG 知识图谱检索

**需求描述**：新增图检索通道。摄取端用 LLM 从文本块抽取（实体-关系-实体）三元组存入 Supabase 关系表；检索端从问题提取实体，SQL 遍历一跳关系得到"子图文本"，与向量/关键词三路融合（RRF）后进 rerank。

**验收标准**：
1. 多跳测试集准确率对比：接入图通道后比纯混合检索提升（参考业界 23% → 87% 的跃迁，个人项目目标提升 ≥ 15 个百分点）
2. 关系表数据正确性：人工抽查 50 个三元组，语义正确率 ≥ 90%
3. 新增图通道不显著拖慢检索（增加 < 300ms）

**优先级**：P2（工作量最大，收益最大）

### FR11：对话与偏好记忆（L4 认知记忆入门）

**需求描述**：对话落库（conversations/messages 表，含引用快照），会话结束生成摘要存 user_memories，问答前检索相关历史偏好注入 system prompt。

**验收标准**：
1. 刷新页面后历史对话可恢复
2. 同一用户跨会话偏好可被引用（如"上次你说过喜欢简洁回答"类上下文）
3. 记忆注入不污染当前轮答案（注入内容与问题相关性由人工抽查）

**优先级**：P2
